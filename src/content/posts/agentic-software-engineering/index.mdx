<p class="lede">
  Code generation is becoming abundant. <strong>Engineering judgment is not.</strong> The real
  leverage comes from turning product intent into architecture, executable constraints,
  reviewable changes, and production evidence.
</p>

If you want to demonstrate that you can build with AI, don't publish only the final code. Show the decisions, trade-offs, specifications, quality gates, and recovery paths that made the result trustworthy. That is the strongest quality signal because it reveals how you think, not merely how quickly a model can type.

This is the process I used while building [Claude-Lens](https://github.com/foyzulkarim/claude-lens) in public. It is not a universal framework, but it is a practical one. The division of responsibility is explicit:

- **The model** proposes and executes.
- **The engineer**
  - defines the system;
  - constrains the work;
  - evaluates the evidence;
  - owns the consequences.

<Eyebrow num="Phase 01">Concept</Eyebrow>

## Prototype the experience before production code

Start by exploring _what_ you want to build: the user, the problem, the core journey, and the smallest outcome worth shipping. Do not commit to a production technology stack yet. At this point the important questions are: who is this for, what job are they trying to complete, and what would make the result meaningfully better than their current option?

Once the product shape is clear, use Claude Design, Lovable, Google Stitch, or another design tool to generate the screens. I kept the output deliberately lightweight: raw HTML and CSS rather than a production React application. That prototype code is disposable; its job is to make the idea concrete enough to critique.

I then rendered each screen to a reference PNG. A multimodal model can compare the implemented UI with that visual target, while browser automation can later turn the same reference into repeatable visual checks. The image is not a complete specification—it cannot prove behaviour, accessibility, responsiveness, or performance—but it is a useful oracle for layout and visual intent.

The deliverables from Phase 1 are small and explicit: a user journey, screen prototypes, reference images, and a first list of measurable outcomes. No production implementation yet.

<Eyebrow num="Phase 02">Architect</Eyebrow>

## Separate product features from the foundation beneath them

Now bring the prototypes into an architectural conversation. Identify two classes of work: **product capabilities**, which users can see, and **foundational capabilities**, which make those features possible—routing, identity, data ownership, persistence, error handling, test infrastructure, security boundaries, and observability.

Technology selection belongs here, after the constraints are visible. For Claude-Lens, the data model forced the useful debate: do we need Postgres, what are the read and write patterns, what should be stored as snapshots, and where do deltas make more sense? Ask the model for at least two viable designs, their failure modes, operational cost, and the conditions that would invalidate each choice.

The model can widen the option space, but it cannot own the decision. Record consequential choices as short architecture decision records: context, options, decision, consequences, and a revisit trigger. This prevents a confident chat response from silently becoming permanent architecture.

### Split the foundation into runnable tasks

The foundation is not one giant commit. Split it into thin, verifiable increments: `npm start` boots the application; one route resolves; one migration applies; one health check reports dependencies; one telemetry signal reaches the local collector. Every task should leave the repository runnable and produce evidence that the new capability works.

### Don't go cheap on testing, either

Use the cheapest test that can detect the failure you care about: unit tests for isolated logic, integration tests for boundaries such as database behaviour, contract tests between services, and a smaller set of end-to-end tests for critical journeys using tools such as Playwright or Cypress.

For database integration, [Testcontainers](https://testcontainers.com/guides/introducing-testcontainers/) starts a disposable instance of the same kind of service you use in production. Run the real migration, exercise inserts and queries against that container, and tear it down afterwards. It is slower than an in-memory substitute, but it catches a different and valuable class of failure.

For the UI, browser tests should assert behaviour first. Add visual regression only where appearance is part of the contract. [Playwright's screenshot assertions](https://playwright.dev/docs/test-snapshots) can compare a page with a checked-in baseline, but the rendering environment must remain consistent or the test becomes noisy.

<Callout tag="The quality principle">
  **Executable evidence scales better than prompts.** As agents generate more code than a human
  can inspect line by line, tests, type checks, linters, security scans, and acceptance artefacts
  become the control plane. They do not remove the need for review; they focus review on
  behaviour, risk, and design.
</Callout>

When the plan is complete, you have the blueprint for a **runnable application with zero product features**. You have not implemented it yet; you have made the work independently verifiable.

<Eyebrow num="Phase 03">Features &amp; spec</Eyebrow>

## Turn screens into contracts, then contracts into tickets

Claude-Lens started with 12 screens when I first planned it, but screens are not a delivery plan. Each capability had dependencies, data requirements, failure states, and non-functional constraints. I first mapped that dependency graph, then cut the work into vertical slices that could be demonstrated and tested independently.

You _choreograph_ the tasks: what must happen first, what can run in parallel, and what evidence unlocks the next step. Do not rely on holding the entire system in your head. Keep the dependency map, architecture decisions, domain vocabulary, and invariants in the repository so that both humans and agents work from the same versioned context.

### Flesh each feature into a real ticket

Pick one capability—say the dashboard—and ask the model to inspect the reference, identify components and states, and expose missing decisions. My development pipeline turns that conversation into a consistent ticket through two agent skills. The first captures the thinking in the repository as `issue-<number>.md`; the second creates the corresponding GitHub issue from that file. The duplication is intentional: keeping the issue specifications in the repository gives the agent the full orchestration context as it works through them locally.

A useful ticket contains:

- the user outcome and relevant business rule;
- inputs, outputs, routes, data ownership, and invariants;
- acceptance criteria, including empty, loading, error, and permission states;
- the test strategy and required evidence;
- performance, accessibility, security, and observability constraints where relevant;
- explicit non-goals, dependencies, and rollback considerations.

This is enough detail to constrain the implementation without prescribing every line. For UI work, Playwright can boot the application, perform the journey, assert behaviour, capture the result, and compare selected screens with the Phase 1 references.

### The spec is everything, sitting in your repo

Repeat this for every capability and you are still not implementing—you are reducing ambiguity. Review the complete path over several sessions, from architecture through the final acceptance criterion. The resulting specification lives beside the code, changes through pull requests, and remains traceable to the delivered behaviour.

Do not feed one enormous specification to an agent and hope it preserves every constraint. Give each task the smallest sufficient context, link to canonical artefacts, and require the agent to restate its understanding before it changes the repository.

### Automate the ticketing

I used GitHub Issues as the execution queue and automated the publishing step. The important property is not the script; it is **idempotency**. Give every local task a stable identifier, persist the remote issue number, and use explicit states such as `draft`, `published`, and `closed`. Re-running the synchroniser should update the intended issue, never create a duplicate.

## Now — and only now — the implementation loop

You now have sequenced issues, bounded context, and explicit gates. _Now_ implementation starts. For each ticket, ask the agent to restate the requirement, identify ambiguity and risk, and propose a short plan. Resolve misunderstandings before granting write access. Then run the same loop for every change.

Some independent tickets can now run in parallel. [Git worktrees](https://git-scm.com/docs/git-worktree) let one repository check out multiple branches into separate working directories, giving each agent an isolated filesystem view without cloning the repository repeatedly.

Parallelism is not automatically throughput. Agents can still collide through shared APIs, ports, databases, generated files, or incompatible migrations. Cap concurrency at the review and integration capacity of the team, assign clear file or subsystem ownership, and merge small changes frequently.

### Give the agent less authority than the engineer

An agent that can edit code, run commands, open pull requests, and reach cloud services has a meaningful blast radius. Apply least privilege: use a disposable environment, keep production credentials out of the workspace, separate read and write capabilities, require approval for destructive or external actions, and protect the main branch. OWASP's [AI Agent Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/AI_Agent_Security_Cheat_Sheet.html) recommends the same basic pattern: minimum tools, scoped permissions, and explicit authorisation for sensitive operations.

Each pull request should carry evidence: tests executed, screenshots or traces where relevant, migrations reviewed, risks noted, and rollback considered. Bugs become issues and travel through the same loop. The process should become repeatable, not thoughtless.

<Eyebrow num="Phase 05">Operate</Eyebrow>

## Shipping is another hypothesis, not the finish line

A feature that passed CI can still fail under real data, real latency, real permissions, and real user behaviour. Define the production check before deployment: what metric should move, what error budget is acceptable, how will you detect a regression, and what is the rollback path?

Instrument the system as part of the feature, not as post-release cleanup. [OpenTelemetry describes observability](https://opentelemetry.io/docs/concepts/observability-primer/) through signals such as traces, metrics, and logs; together they let you investigate failures you did not predict when writing the tests. Correlate those signals with the release and the acceptance criteria.

Then close the loop: compare production evidence with the intended outcome, turn surprises into new tickets, and update the specification when the system teaches you something. An agentic lifecycle is valuable because every phase produces artefacts that constrain and improve the next one.

<Callout tag="The ownership principle">
  **The human remains accountable.** Models can generate options, code, tests, and reviews. They
  cannot accept business risk, resolve stakeholder trade-offs, or own a production incident.
  Faster execution increases the value of judgment; it does not replace it.
</Callout>

## The difference is not the model. It is the control loop.

Vibe coding is useful for exploration: prompt, inspect, adjust, repeat. It becomes dangerous when that improvisation is mistaken for a production process.

Agentic software engineering adds the missing discipline: explicit intent, architecture, bounded tasks, executable acceptance criteria, constrained execution, independent review, and operational feedback. If you build in public, publish those artefacts as well as the final application. They are the evidence that you engineered the system rather than merely generated it.
