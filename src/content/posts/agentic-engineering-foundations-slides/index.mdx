<section class="slide" data-label="07 The Hook" aria-label="What is an LLM">
  <div class="slide-body">
    <div class="slide-meta"><span class="gold">The Hook</span><span>07</span></div>
    <h1 class="slide-title">What Is a Large Language Model?</h1>

    <div class="grid cols-2" style="gap: 24px; margin-bottom: 24px;">
      <div class="card">
        <div class="label-caps gold">Definition</div>
        <p style="font-size: 22px; line-height: 1.55; margin-top: 8px;">A statistical model trained on text to predict the next token. No memory, no awareness — just pattern matching at scale.</p>
      </div>
      <div class="card">
        <div class="label-caps teal">The Breakthrough</div>
        <p style="font-size: 22px; line-height: 1.55; margin-top: 8px;">The transformer: parallel attention over the whole context at once. Long-range coherence at scale — the architecture that made agents possible.</p>
      </div>
    </div>

    <div class="label-caps gold" style="margin-bottom: 16px;">The Four Pillars</div>
    <div class="grid cols-4" style="flex: 1; gap: 18px;">
      <div class="card flex-col" style="padding: 22px;">
        <div class="card-num">01</div>
        <div class="card-h" style="font-size: 22px; margin: 6px 0 10px 0;">Pre-training</div>
        <ul class="bullets" style="gap: 8px;"><li style="font-size: 22px;">Trained on billions of documents</li><li style="font-size: 22px;">Absorbs patterns by exposure</li><li style="font-size: 22px;">Predicts patterns, not meaning</li></ul>
      </div>
      <div class="card flex-col" style="padding: 22px;">
        <div class="card-num">02</div>
        <div class="card-h" style="font-size: 22px; margin: 6px 0 10px 0;">Next-Token Prediction</div>
        <ul class="bullets" style="gap: 8px;"><li style="font-size: 22px;">Predicts the next likely token</li><li style="font-size: 22px;">Adds it back, repeats</li><li style="font-size: 22px;">Simple mechanism, intelligent output</li></ul>
      </div>
      <div class="card flex-col" style="padding: 22px;">
        <div class="card-num">03</div>
        <div class="card-h" style="font-size: 22px; margin: 6px 0 10px 0;">Emergent Capabilities</div>
        <ul class="bullets" style="gap: 8px;"><li style="font-size: 22px;">Small: completes sentences</li><li style="font-size: 22px;">Medium: summarizes paragraphs</li><li style="font-size: 22px;">Large: writes code, debugs, reasons</li></ul>
      </div>
      <div class="card flex-col" style="padding: 22px;">
        <div class="card-num">04</div>
        <div class="card-h" style="font-size: 22px; margin: 6px 0 10px 0;">Transformer Arch</div>
        <ul class="bullets" style="gap: 8px;"><li style="font-size: 22px;">Looks at all words at once</li><li style="font-size: 22px;">Decides which parts matter</li><li style="font-size: 22px;">Long-range coherence</li></ul>
      </div>
    </div>
    <div class="takeaway" style="background: var(--deck-tint-red); border-left-color: var(--deck-red);"><span class="arrow" style="color: var(--deck-red);">!</span>Hard limits: finite context window (&#126;200K tokens) · no persistent memory across sessions · KV-cache is working memory, not true memory.</div>
  </div>
</section>

<section class="slide" data-label="08 The Hook" aria-label="How LLMs power agents">
  <div class="slide-body">
    <div class="slide-meta"><span class="gold">The Hook</span><span>08</span></div>
    <h1 class="slide-title">How LLMs Power Agents</h1>
    <p class="slide-lede">The LLM is the brain. The agent is the body.</p>

    <div class="grid cols-4" style="flex: 1; gap: 18px;">
      <div class="card flex-col">
        <div class="card-num">01</div>
        <div class="card-h" style="margin: 6px 0 8px 0;">Intent</div>
        <div class="fine" style="font-size: 22px;">You state what you want in natural language. The LLM parses words into a structured goal.</div>
        <div class="card-foot" style="font-size: 22px;">LLM parses → structured goal</div>
      </div>
      <div class="card flex-col">
        <div class="card-num">02</div>
        <div class="card-h" style="margin: 6px 0 8px 0;">Breakdown</div>
        <div class="fine" style="font-size: 22px;">The LLM decomposes the goal into steps. Route → schema → validation → query → errors.</div>
        <div class="card-foot" style="font-size: 22px;">LLM plans → executable steps</div>
      </div>
      <div class="card flex-col">
        <div class="card-num">03</div>
        <div class="card-h" style="margin: 6px 0 8px 0;">Execution</div>
        <div class="fine" style="font-size: 22px;">The LLM generates the actual code — functions, SQL migrations, test cases.</div>
        <div class="card-foot" style="font-size: 22px;">LLM builds → working code</div>
      </div>
      <div class="card flex-col">
        <div class="card-num">04</div>
        <div class="card-h" style="margin: 6px 0 8px 0;">Loopback</div>
        <div class="fine" style="font-size: 22px;">The LLM evaluates the result. Tests pass? Secure? Generates fix if needed.</div>
        <div class="card-foot" style="font-size: 22px;">LLM checks → adapts → repeats</div>
      </div>
    </div>
    <div class="fine" style="font-size: 18px; color: var(--deck-text-mute); margin-bottom: 8px; text-align: center;">Also known as: <em>perceive-plan-act-observe</em> · <em>ReAct</em> · <em>OODA</em> — same pattern, different names.</div>
    <div class="takeaway"><span class="arrow">→</span>The quality of the loop is determined by the quality of the intent. Vague prompts → vague breakdown → vague code. The framework gives you structure. Specificity gives you precision.</div>
  </div>
</section>

        <div style="font-size: 21px; line-height: 1.6; color: var(--deck-text);">Each tool call adds to the context. After ten calls, you've sent the original prompt ten times plus ten growing result payloads. The context window fills faster than it looks from outside.</div>
      </div>
    </div>
    <div class="takeaway"><span class="arrow">→</span>One thing you ask for can be ten turns under the hood — and the context grows with every one.</div>
  </div>

<section class="slide" data-label="21F The First Fix" aria-label="KV cache compute once">
  <div class="slide-body">
    <div class="slide-meta"><span class="gold">Under the Hood &nbsp;·&nbsp; The First Fix</span><span>21F</span></div>
    <h1 class="slide-title">KV Cache: Compute Once, Reuse</h1>
    <p class="slide-lede"><span class="psbadge solution">Solution 1</span>&nbsp;&nbsp;To emit each new token, attention must look at the <em>Key</em> and <em>Value</em> of every earlier token. So compute each token's K/V <em>once</em>, store them, and reuse — instead of re-deriving the whole history at every step.</p>
    <div class="label-caps gold" style="font-size: 16px; margin-bottom: 8px;">Attention = a soft dictionary lookup</div>
    <div class="grid cols-3" style="gap: 18px; margin-bottom: 18px; flex-shrink: 0;">
      <div class="card tight" style="border-left: 3px solid var(--deck-text-mute);">
        <div class="label-caps" style="color: var(--deck-text-dim); margin-bottom: 4px;">Query (Q)</div>
        <div style="font-size: 18px; line-height: 1.4; color: var(--deck-text);">What the current token is <em>looking for</em>. Used once, then dropped — never stored.</div>
      </div>
      <div class="card tight" style="border-left: 3px solid var(--deck-gold);">
        <div class="label-caps gold" style="margin-bottom: 4px;">Key (K)</div>
        <div style="font-size: 18px; line-height: 1.4; color: var(--deck-text);">The <em>label</em> a token advertises — what every later Query matches against.</div>
      </div>
      <div class="card tight" style="border-left: 3px solid var(--deck-teal);">
        <div class="label-caps teal" style="margin-bottom: 4px;">Value (V)</div>
        <div style="font-size: 18px; line-height: 1.4; color: var(--deck-text);">The <em>content</em> a token hands over when its Key gets matched.</div>
      </div>
    </div>
    <div class="grid cols-2" style="flex: 1; gap: 24px; margin-bottom: 16px;">
      <div class="card flex-col">
        <div class="label-caps gold" style="margin-bottom: 10px;">During Prefill</div>
        <div style="font-size: 21px; line-height: 1.5; color: var(--deck-text);">Compute K and V for <em>all</em> input tokens in one parallel pass, and <span class="gold">write them to the store</span>. One-time cost.</div>
        <div class="fine" style="font-size: 16px; color: var(--deck-text-dim); margin-top: auto; padding-top: 10px;">All input tokens → K/V → stored</div>
      </div>
      <div class="card flex-col">
        <div class="label-caps teal" style="margin-bottom: 10px;">During Decode</div>
        <div style="font-size: 21px; line-height: 1.5; color: var(--deck-text);">Each new token's Query <span class="teal">reads the whole stored K/V</span>, emits a token, then <em>appends</em> its own K/V. One new row per step.</div>
        <div class="fine" style="font-size: 16px; color: var(--deck-text-dim); margin-top: auto; padding-top: 10px;">Read store → emit → append → repeat</div>
      </div>
    </div>
    <div class="card tight" style="border-left: 3px solid var(--deck-red); background: var(--deck-tint-red); flex-shrink: 0;">
      <div style="font-size: 19px; line-height: 1.55; color: var(--deck-text);">Think of a game checkpoint — instead of replaying from level 1 each time you want to advance one step, you save progress and resume from there. Without the KV store, every decode step would re-derive K/V for all prior tokens — quadratic. The store <em>is</em> that checkpoint: each token's K/V computed <span class="gold">once</span>, reused forever after. But the checkpoint is <span class="red">ephemeral</span> — it is wiped when the response ends, so the next turn must re-prefill the stable prefix from scratch.</div>
    </div>
    <div class="takeaway"><span class="arrow">→</span>Compute once, reuse — within one response. Next: inside the lookup itself, to see how attention actually reads these K/V rows — then where this store lives, and why it dies when the response ends.</div>
  </div>
</section>

<section class="slide" data-label="21F2 How Attention Picks" aria-label="Inside the lookup">
  <div class="slide-body">
    <div class="slide-meta"><span class="gold">Under the Hood &nbsp;·&nbsp; How Attention Picks</span><span>21F2</span></div>
    <h1 class="slide-title">Inside the Lookup: How Attention Picks</h1>
    <p class="slide-lede">Previously we called attention a <em>soft dictionary lookup</em>. Here's the actual mechanic — three steps that turn the current token's <span class="gold">Query</span> into one blended answer. Worked on a real sentence.</p>
    <div class="card tight" style="border-left: 3px solid var(--deck-gold); background: var(--deck-tint-gold); flex-shrink: 0; margin-bottom: 18px;">
      <div style="font-size: 21px; line-height: 1.5; color: var(--deck-text);">"The <span class="teal">cat</span> sat on the <span class="teal">mat</span> because <span class="gold" style="font-weight: 600;">it</span> was tired."&nbsp;&nbsp;— processing <span class="gold" style="font-weight: 600;">"it"</span>, whose Query asks: <em>which earlier token do I refer to?</em> It compares against every earlier token's <span class="gold">Key</span>.</div>
    </div>
    <div class="grid cols-3" style="flex: 1; gap: 24px; margin-bottom: 18px;">
      <div class="card flex-col">
        <div class="label-caps gold" style="margin-bottom: 8px;">Step 1 &nbsp;·&nbsp; Dot-product</div>
        <div style="font-size: 20px; line-height: 1.45; color: var(--deck-text);">Multiply "it"'s Query by each Key → one <em>relevance score</em> per token. Bigger = better match.</div>
        <div class="fine mono" style="font-size: 17px; color: var(--deck-text-dim); margin-top: auto; padding-top: 12px; line-height: 1.7;">cat&nbsp;&nbsp;9.1<br />mat&nbsp;&nbsp;4.0<br />sat&nbsp;&nbsp;0.3<br />the&nbsp;&nbsp;0.1</div>
      </div>
      <div class="card flex-col">
        <div class="label-caps red" style="margin-bottom: 8px; color: var(--deck-red);">Step 2 &nbsp;·&nbsp; Softmax</div>
        <div style="font-size: 20px; line-height: 1.45; color: var(--deck-text);">Squash the scores into <em>percentages that sum to 100%</em> — the attention weights.</div>
        <div class="fine mono" style="font-size: 17px; color: var(--deck-text-dim); margin-top: auto; padding-top: 12px; line-height: 1.7;">cat&nbsp;&nbsp;85%<br />mat&nbsp;&nbsp;10%<br />sat&nbsp;&nbsp;&nbsp;3%<br />the&nbsp;&nbsp;&nbsp;2%</div>
      </div>
      <div class="card flex-col">
        <div class="label-caps teal" style="margin-bottom: 8px;">Step 3 &nbsp;·&nbsp; Weighted blend</div>
        <div style="font-size: 20px; line-height: 1.45; color: var(--deck-text);">Add up each token's <em>Value</em> times its weight. The result is one vector — mostly <span class="teal">cat</span>'s content.</div>
        <div class="fine mono" style="font-size: 16px; color: var(--deck-text-dim); margin-top: auto; padding-top: 12px; line-height: 1.6;">.85·V(cat)<br />+ .10·V(mat)<br />+ .03·V(sat) …<br /><span class="teal">→ "it" ≈ cat</span></div>
      </div>
    </div>
    <div class="takeaway"><span class="arrow">→</span>It never returns one entry — it returns a <em>blend</em> of all Values, weighted by relevance. That's the "soft." And it reads <em>every</em> stored Key/Value to do it — which is why the whole history must stay in the KV store.</div>
  </div>
</section>

<section class="slide" data-label="21G The Boxes" aria-label="Where the KV cache lives">
  <div class="slide-body">
    <div class="slide-meta"><span class="gold">Under the Hood &nbsp;·&nbsp; The Boxes</span><span>21G</span></div>
    <h1 class="slide-title">Where the KV Cache Lives</h1>
    <p class="slide-lede">The cache is <em>not</em> inside the model's weights. Inside the <em>inference server</em> there are three distinct regions — and your tokens' K/V only ever land in one of them.</p>
    <div style="flex: 1; display: flex; flex-direction: column; gap: 18px; min-height: 0;">
      <div class="grid cols-2" style="gap: 24px; flex: 1; min-height: 0;">
        <div class="card flex-col" style="border-left: 4px solid var(--deck-gold);">
          <div class="label-caps gold" style="margin-bottom: 10px;">① Weights — the model</div>
          <div style="font-size: 20px; line-height: 1.5; color: var(--deck-text);">The <em>weight matrices</em> W<sub>Q</sub>, W<sub>K</sub>, W<sub>V</sub> and the <em>MLP</em> — loaded <em>once</em> at boot, shared by every request. <span class="gold">Read-only. Never changed. Never cleared.</span> Your tokens never go <em>into</em> them.</div>
          <div class="fine" style="font-size: 15px; color: var(--deck-text-dim); margin-top: auto; padding-top: 10px;">The machinery — fixed</div>
        </div>
        <div class="card flex-col" style="border-left: 4px solid var(--deck-teal);">
          <div class="label-caps teal" style="margin-bottom: 10px;">② KV Cache Store <span style="color: var(--deck-text-mute); text-transform: none; letter-spacing: 0; font-weight: 500;">(the "store" and the "cache" are the same thing — two words, one memory region)</span></div>
          <div style="font-size: 20px; line-height: 1.5; color: var(--deck-text);">A <em>separate</em> memory region holding the per-token K/V stack. <span class="teal">Read + write. Grows one row per token.</span> The only region that holds <em>your</em> data.</div>
          <div class="fine" style="font-size: 15px; color: var(--deck-text-dim); margin-top: auto; padding-top: 10px;">The prep table — fills up, kept or wiped</div>
        </div>
      </div>
      <div class="card" style="border-left: 4px solid var(--deck-text-mute); flex-shrink: 0;">
        <div class="label-caps" style="color: var(--deck-text-dim); margin-bottom: 8px;">③ Forward Pass — the compute</div>
        <div style="font-size: 20px; line-height: 1.5; color: var(--deck-text);">Token in → <em>matmuls</em> → token out. <span class="gold">Reads the weights</span> and <span class="teal">reads + appends the KV store</span>. Transient — nothing persists here.</div>
      </div>
    </div>
    <div class="card tight" style="border-left: 3px solid var(--deck-gold); background: var(--deck-tint-gold); flex-shrink: 0; margin-top: 14px;">
      <div style="font-size: 19px; line-height: 1.5; color: var(--deck-text);">At the end of a response the runtime <em>frees</em> region ② by default — region ① is untouched, ready for the next request. <span class="gold">So the only thing worth keeping alive is the KV store.</span> <span class="fine" style="color: var(--deck-text-mute); font-size: 15px;">(At scale, region ② can be offloaded to other memory tiers or nodes.)</span></div>
    </div>
    <div class="takeaway"><span class="arrow">→</span>Weights = fixed machinery. KV cache = a separate store beside it, never part of the model — which is exactly why it <em>can</em> outlive one request.</div>
  </div>
</section>

<section class="slide" data-label="21H0 What Caching Skips" aria-label="What caching actually skips">
  <div class="slide-body">
    <div class="slide-meta"><span class="gold">Under the Hood &nbsp;·&nbsp; What Caching Skips</span><span>21H0</span></div>
    <h1 class="slide-title">What Caching Actually Skips</h1>
    <p class="slide-lede">Back to the three stages from 21E1. Two of them get confused — and only one is ever cached. The trap: thinking "tokens are already computed, so what's left to cache?"</p>
    <div style="display: flex; align-items: stretch; gap: 14px; flex-shrink: 0; margin-bottom: 18px;">
      <div class="card tight" style="flex: 1; border-left: 3px solid var(--deck-text-mute);">
        <div class="label-caps" style="color: var(--deck-text-dim); margin-bottom: 4px;">① Tokenize</div>
        <div style="font-size: 17px; line-height: 1.4; color: var(--deck-text);">text → token IDs<br /><span class="fine">"The cat" → [464, 2415]</span></div>
        <div class="fine" style="font-size: 14px; color: var(--deck-text-dim); margin-top: 6px;">Always runs · &#126;free · CPU</div>
      </div>
      <div style="align-self: center; color: var(--deck-text-mute); font-size: 24px;">→</div>
      <div class="card tight" style="flex: 1.3; border-left: 3px solid var(--deck-red);">
        <div class="label-caps red" style="margin-bottom: 4px; color: var(--deck-red);">② Prefill — compute K/V</div>
        <div style="font-size: 17px; line-height: 1.4; color: var(--deck-text);">each token ID → vector → W<sub>K</sub>/W<sub>V</sub> matmul → its <span class="gold">Key</span> + <span class="teal">Value</span></div>
        <div class="fine red" style="font-size: 14px; margin-top: 6px; color: var(--deck-red);">Expensive · GPU · the forward pass</div>
      </div>
      <div style="align-self: center; color: var(--deck-text-mute); font-size: 24px;">→</div>
      <div class="card tight" style="flex: 1; border-left: 3px solid var(--deck-teal);">
        <div class="label-caps teal" style="margin-bottom: 4px;">③ Decode</div>
        <div style="font-size: 17px; line-height: 1.4; color: var(--deck-text);">emit output tokens one at a time, reading the whole K/V store</div>
        <div class="fine" style="font-size: 14px; color: var(--deck-text-dim); margin-top: 6px;">Serial · output cost</div>
      </div>
    </div>
    <div class="grid cols-2" style="flex: 1; gap: 24px; margin-bottom: 16px;">
      <div class="card flex-col" style="border-left: 4px solid var(--deck-red);">
        <div class="label-caps red" style="margin-bottom: 10px; color: var(--deck-red);">The confusion</div>
        <div style="font-size: 21px; line-height: 1.5; color: var(--deck-text);">A token's K and V are produced <em>by</em> the forward pass (stage ②) — they don't exist after tokenizing. So "tokens are already computed" only means stage ①. The expensive K/V work hasn't happened yet.</div>
      </div>
      <div class="card flex-col" style="border-left: 4px solid var(--deck-gold);">
        <div class="label-caps gold" style="margin-bottom: 10px;">Where caching enters</div>
        <div style="font-size: 21px; line-height: 1.5; color: var(--deck-text);">Hash the prefix token IDs → look in the store. <span class="teal">Hit</span> → load stored K/V, <span class="gold">skip stage ②</span> for them. <span class="red">Miss</span> → run stage ② and store it. Stage ① still runs either way.</div>
      </div>
    </div>
    <div class="takeaway"><span class="arrow">→</span>Caching never skips tokenization. It skips the <em>forward-pass K/V computation</em> for the unchanged prefix — the only part that was ever expensive.</div>
  </div>
</section>

<section class="slide" data-label="21H1 The Solution" aria-label="Prompt caching same store">
  <div class="slide-body">
    <div class="slide-meta"><span class="gold">Under the Hood &nbsp;·&nbsp; The Solution</span><span>21H1</span></div>
    <h1 class="slide-title">Prompt Caching: Same Store, Kept Warm</h1>
    <p class="slide-lede"><span class="psbadge solution">Solution 2</span>&nbsp;&nbsp;Prompt caching is the <em>same KV store</em> — the server just chooses not to free it. It keeps the prefix's K/V alive across requests, so the next turn <em>loads</em> them instead of re-prefilling. You still send everything every turn; the server stays stateless.</p>
    <div class="grid cols-2" style="flex: 1; gap: 24px; margin-bottom: 16px;">
      <div class="card flex-col" style="border-left: 4px solid var(--deck-gold);">
        <div class="label-caps gold" style="margin-bottom: 10px;">Request 1 — cache write</div>
        <div style="font-size: 20px; line-height: 1.5; color: var(--deck-text);">Full prefill of the prefix — system prompt, tools, CLAUDE.md. Its K/V is computed and <span class="gold">kept in the store</span>, keyed by a <em>hash</em> of the prefix tokens.</div>
        <div class="fine" style="font-size: 16px; color: var(--deck-text-dim); margin-top: auto; padding-top: 10px;">Write ≈ 1.25× input price · once</div>
      </div>
      <div class="card flex-col" style="border-left: 4px solid var(--deck-teal);">
        <div class="label-caps teal" style="margin-bottom: 10px;">Request 2 — cache hit</div>
        <div style="font-size: 20px; line-height: 1.5; color: var(--deck-text);">Same prefix → hash matches → <span class="teal">load the stored K/V</span>, skip its prefill. Only the new tail is prefilled. The match runs token-by-token until your context diverges.</div>
        <div class="fine" style="font-size: 16px; color: var(--deck-text-dim); margin-top: auto; padding-top: 10px;">Read ≈ 10% input price · every hit</div>
      </div>
    </div>
    <div class="grid cols-2" style="gap: 20px;">
      <div class="card" style="border-left: 3px solid var(--deck-gold); background: var(--deck-tint-gold);">
        <div class="label-caps gold" style="margin-bottom: 8px;">Same store, two lifetimes</div>
        <div style="font-size: 18px; line-height: 1.5; color: var(--deck-text);"><span class="gold">Within a response:</span> built during prefill + decode, freed when it returns.<br /><span class="teal">Across requests:</span> the prefix's K/V is <em>retained</em>.<br /><span style="font-size: 16px; color: var(--deck-text-mute);">Prompt caching is the KV cache the server didn't throw away.</span></div>
      </div>
      <div class="card">
        <div class="label-caps" style="margin-bottom: 8px; color: var(--deck-text-dim);">TTL &nbsp;·&nbsp; until evicted</div>
        <div style="font-size: 18px; line-height: 1.5; color: var(--deck-text);">Entries leave two ways: <span class="gold">TTL expiry</span> — the entry times out after &#126;5 min idle (refreshed on each hit) — or <span class="gold">memory-pressure eviction</span> — the server runs out of room and drops older entries to make space. Let it lapse → re-prefill at full cost.</div>
      </div>
    </div>
    <div class="takeaway"><span class="arrow">→</span>Caching keys on the <em>prefix</em>. Whatever stays identical at the front rides cheap. Change something early — even one token — and the cache breaks from that point on.</div>
  </div>
</section>
